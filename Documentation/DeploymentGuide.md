# Deployment Guide

## Prerequisites

- .NET 9 SDK/Runtime on the host machine (project targets net9.0; see [ModuleStatus.md](ModuleStatus.md) for
  the planned .NET 10 upgrade).
- SQL Server 2019+ (Express is sufficient for a single pharmacy). **Recommended topology: SQL Server and the
  web application run on the same Windows machine.** Module 13's backup feature, and the simplest security
  posture generally, both assume this — a remote SQL Server works too, but then `BackupSettings:DirectoryPath`
  needs to be a path both the web app's process and the SQL Server service account can reach (e.g. a UNC
  share), which is extra setup the single-machine case avoids entirely.
- SQL Server Management Studio (SSMS), for running `Database/PharmaDesk_Complete.sql` and, if ever needed,
  a restore script generated by the Backup module.

## Running locally (development)

```powershell
# From the repository root
dotnet build

# Apply the schema (first time, or after pulling an update to Database/PharmaDesk_Complete.sql)
sqlcmd -S <your-server> -E -i Database\PharmaDesk_Complete.sql

# Set the connection string (PharmaDesk.Web/appsettings.Development.json)
#   "ConnectionStrings": { "DefaultConnection": "Server=<your-server>;Database=PharmaDesk;Trusted_Connection=True;TrustServerCertificate=True;" }

dotnet run --project PharmaDesk.Web
```

The app listens on the URL printed to the console (see `PharmaDesk.Web/Properties/launchSettings.json` for the
default ports) and serves the dashboard at `/`. Without a reachable database, pages that need one show a
graceful "temporarily unavailable" message or status banner rather than crashing — this is deliberate and
documented throughout `ModuleStatus.md`.

## Production deployment

### 1. Publish the application

```powershell
dotnet publish PharmaDesk.Web -c Release -o C:\PharmaDesk\app
```

### 2. Choose a host

**Recommended: IIS with the ASP.NET Core Module**, since it's the most common pattern for Windows on-prem
line-of-business software and integrates with Windows admin tooling your IT support already knows:

1. Install the [.NET 9 Hosting Bundle](https://dotnet.microsoft.com/download/dotnet/9.0) on the server (this
   installs the ASP.NET Core Module for IIS).
2. Create an IIS site pointed at `C:\PharmaDesk\app`, with an Application Pool set to **No Managed Code**
   (the ASP.NET Core Module handles the runtime, not IIS's own CLR hosting).
3. Bind the site to HTTPS with a real certificate (see below) — `UseHttpsRedirection`/`UseHsts` are already
   configured in the app and expect one.

**Alternative: Kestrel as a Windows Service.** If IIS isn't available, `dotnet PharmaDesk.Web.dll` can run
directly as a Windows Service (via `sc create` or `New-Service`, pointing at the published `.exe`). This
needs its own reverse proxy or direct HTTPS binding configured in `appsettings.json`'s Kestrel section,
which this guide doesn't detail further — IIS is the better-supported path for now.

### 3. HTTPS certificate

The app already enforces HTTPS (`UseHttpsRedirection`) and sends `Strict-Transport-Security` in Production
(`UseHsts`) — both require a certificate bound to the site before the app will behave correctly:

- For a pharmacy's internal network, a self-signed certificate installed into the server's trusted root
  store (and distributed to client machines) is a reasonable, low-cost option.
- For anything internet-reachable, use a real certificate (e.g. from a public CA); self-signed certificates
  will trigger browser warnings for anyone who hasn't explicitly trusted it.

### 4. Keep the connection string out of a committed `appsettings.json`

`appsettings.json` ships with a placeholder `Trusted_Connection=True` connection string meant for local
development. For a real deployment, override it with an environment variable rather than editing and
distributing the file with a production value baked in:

```powershell
# IIS: set in the Application Pool's or site's environment variables (or via web.config)
$env:ConnectionStrings__DefaultConnection = "Server=localhost;Database=PharmaDesk;Trusted_Connection=True;TrustServerCertificate=True;"
```

ASP.NET Core's configuration system reads environment variables with `__` as the section separator, so this
overrides `ConnectionStrings:DefaultConnection` without touching the file at all — the same mechanism works
for `BackupSettings__DirectoryPath` if you want to override that per-deployment too.

### 5. Backup folder permissions

Set `BackupSettings:DirectoryPath` (via the environment variable above, or by editing `appsettings.json`
directly if it's not been committed anywhere) to a real folder. **Both the IIS Application Pool identity and
the SQL Server service account need read/write access to this folder** — the web app writes nothing to it
directly (SQL Server itself writes the `.bak` file when `BACKUP DATABASE` runs), but the web app needs to
list, read, and delete files there for the Backup screen to work. On the same-machine topology this is just
normal NTFS permissions on a local folder; grant both accounts Modify rights.

### 6. First-run sequence

1. Run `Database/PharmaDesk_Complete.sql` in SSMS against the target SQL Server instance — safe to re-run,
   it's fully idempotent and version-gated (see `DatabaseUpdateGuide.md`).
2. Start the application (IIS site or the Windows Service).
3. Check the application's log file (`Logs/pharmadesk-*.log`, next to the published app) for a line like
   `Seeded the default admin account. Username: ... Temporary password: ...` — this is logged exactly once,
   the first time the app starts against a fresh database.
4. Log in with that username/temporary password. The app forces an immediate password change before
   anything else is reachable — this is enforced server-side, not just hidden in the UI.
5. Go to **Pharmacy Profile** and replace the seeded placeholder tenant name/details with the real pharmacy
   information, then set up Branches, Users/Roles, and the Medicine catalog before going live.

### 7. What's already hardened vs. what's the operator's responsibility

Already in the application (Module 14):
- CSRF tokens on every state-changing action, server-side permission checks on every controller action,
  account lockout after 5 failed attempts, and a login-endpoint rate limit (10 attempts/minute/IP) on top of
  that lockout.
- `X-Content-Type-Options`, `X-Frame-Options`, and `Referrer-Policy` response headers; HSTS and an
  always-secure auth cookie in Production.
- Tenant data isolation via EF Core query filters (see `Architecture.md`), and a backup/restore story (Module
  13) that never lets the running app execute a destructive `RESTORE DATABASE` on itself.

Still the operator's responsibility:
- The HTTPS certificate itself, and keeping the Windows Server/SQL Server instance patched.
- Firewall rules limiting which machines can reach the site and the SQL Server port.
- Taking the generated backups off-site periodically — Module 13 creates and retains them locally, but
  doesn't copy them anywhere else.
- A real Content-Security-Policy header — explicitly not implemented yet; see `ModuleStatus.md` for why.

### 8. Updating to a new version

1. Stop the application (IIS site or Windows Service).
2. Create a backup first if the Backup screen's automatic daily one isn't recent enough for comfort.
3. Replace the published files with the new version's output.
4. Re-run `Database/PharmaDesk_Complete.sql` — it only applies whatever version blocks haven't been applied
   yet, so running the full file again is always safe.
5. Start the application again.
